# Backend architecture

The internal reference for the Mobile Parts Finder business backend: where each
piece of data lives, who owns it, and how a new module connects without
rebuilding anything.

Written for whoever picks this up next — including me in six months.

---

## 1. What was already here

An audit of the running system, before any of this was added.

| Piece | Where | Notes |
| --- | --- | --- |
| Customer app | `src/app.js` + `src/data/*`, vanilla JS IIFE modules | Routes: `finder`, `models`, `model`, `plans`, `account`, `group` |
| Pre-rendered pages | `finder/`, `models/`, `model/`, `categories/`, generated by `scripts/build-seo.js` | 4,969 pages. Each carries its own `<script>` list |
| Identity | Firebase Authentication, Google provider only | `src/data/firebase.js` |
| Profile | Firestore `users/{uid}` | Written by the browser AND by `/api/profile-sync` |
| Billing | Razorpay, `api/create-order.js` → `api/verify-payment.js` + `api/razorpay-webhook.js` | Idempotent on the payment id |
| Subscriptions | Firestore `subscriptions/{razorpayOrderId}` | One per purchase attempt |
| Payments | Firestore `payments/{razorpayPaymentId}` | Document id **is** the idempotency key |
| Catalogue | `assets/dataset.json`, `assets/search-index.json`, `api/_data/parts.json` | Also imported to Firestore; the CDN copy is what the site reads |
| Rules | `firestore.rules` | Catalogue public, `users/{uid}` owner-only, billing server-only |

**Two things that mattered most and were already right:**

- Access is decided **server side**. `/api/subscription` reads the stored
  record against the server clock; the browser renders what it is told. A
  device clock cannot buy a subscription.
- The profile is **already reused at checkout**. `create-order` reads
  `users/{uid}`, and returns `409 profile-incomplete` naming the missing fields
  rather than asking for details it already has. Part 8 of the brief was
  largely satisfied before this work; what was added is the state model that
  makes it legible, and the guarantee that an empty address never counts as
  incomplete.

**What was missing:** any role concept, any admin surface, any analytics, any
review queue, and any structure for the AI work.

## 2. Single source of truth

This is the rule everything else follows.

```
Firebase Authentication          users/{uid}                     payments / subscriptions
─────────────────────────        ────────────────────────        ────────────────────────
uid                              mobileShopName                  userId  ── joins on uid
auth provider                    proprietorName                  planId, amountPaise
authenticated email              mobileNumber, ...E164           providerPaymentId
emailVerified                    country, countryCode            providerOrderId
created / last sign-in           address (optional)              paymentStatus
disabled                         profilePhotoURL                 startDate / endDate
                                 accountStatus
                                 ── server-written mirror ──
                                 subscriptionStatus
                                 currentPlanId
                                 subscriptionExpiresAt
                                 ── derived mirrors ──
                                 emailLower, mobileShopNameLower,
                                 proprietorNameLower, displayNameLower,
                                 mobileDigits
```

**There is no third copy.** The admin area does not keep its own user table; it
reads these two and joins them by uid at request time. Analytics events,
missing-model requests and AI tasks all reference the uid and never duplicate a
profile field.

Every future module — SEO, Instagram, ads, the LLM — reads business data
through the services in `api/_services/`. None of them gets its own user store.

### Field ownership

| Field group | Owner | Client may write? |
| --- | --- | --- |
| uid, email, provider, auth timestamps | Firebase Auth | no |
| shop name, proprietor, mobile, country, address, photo | the user | yes, own doc only |
| subscription mirror | server (Admin SDK) | **no** — blocked in `firestore.rules` |
| search mirrors (`*Lower`, `mobileDigits`) | server, derived | **no** — same list |
| everything in the admin collections | server | no read, no write |

## 3. Profile completion

Three business facts, and only three:

1. **mobile number, with its country** — `country` is the country-selection
   half of the number, not a fourth requirement. Razorpay Checkout cannot
   prefill a bare `9876543210`.
2. **mobile shop name**
3. **proprietor name**

**Address is optional, permanently.** A returning shop with a complete profile
and a blank address is `profile_complete`. Any code that treats it as a new
user is a bug — there is a test for it in `api/_lib/user-state.test.js`.

### The state model

Three independent axes, deliberately not one enum:

| Axis | Values | Derived from |
| --- | --- | --- |
| `accountState` | `profile_incomplete`, `profile_complete` | the three fields above |
| `subscriptionState` | `subscription_inactive`, `subscription_active` | mirror + **server clock** |
| `accountStatus` | `active`, `disabled`, `suspended` | an operator's decision |

Being signed in is the precondition of all three rather than a value in any of
them — an unauthenticated visitor has no record at all.

One enum would force a choice between `profile_complete` and
`subscription_active` for a user who is both, and whichever you pick, some
screen shows the wrong thing.

Defined once in `api/_schema/user-profile.js`. `REQUIRED_PROFILE_FIELDS` there
is asserted equal to `REQUIRED_PROFILE` in `api/_lib/store.js` by a test —
two lists drifting apart is how a profile passes sign-up and fails at checkout.

## 4. Module layout

```
api/
  _schema/          document shapes and pure derivation. No I/O.
    collections.js          every collection name, with its ownership
    user-profile.js         completion, state derivation, admin view, search mirrors
    billing-records.js      read contract over subscriptions + payments
    analytics-event.js      the event allowlist and metadata filter
    missing-model-request.js normalisation + the status workflow
    roles.js                roles, permissions, the permission table

  _lib/             plumbing. Existing files unchanged; new ones marked.
    firebase.js  http.js  config.js  plans.js  billing-period.js  store.js
    razorpay-signature.js
    admin-auth.js     NEW  requireAdmin / requirePermission / setRole
    pagination.js     NEW  cursors and the page-size ceiling
    validate.js       NEW  every value arriving from outside
    rate-limit.js     NEW  Firestore fixed-window counter

  _services/        domain logic. The only things that touch data.
    user-directory-service.js   search / filter / sort / paginate / detail
    metrics-service.js          dashboard aggregations
    analytics-service.js        event ingest + daily rollups
    missing-model-service.js    the review queue
    audit-service.js            admin action log
    search-service.js           deterministic catalogue lookup
    ai-service.js               the LLM gateway + approval queue
    chatbot-service.js          the assistant pipeline

  admin/            protected routes. Every one calls requireAdmin first.
    session.js  users.js  user.js  metrics.js
    missing-models.js  admins.js  audit.js  ai.js

  events.js         NEW  public analytics ingest
  chat.js           NEW  public assistant
  (existing billing routes unchanged)

admin/index.html    the admin shell — a separate page, not the customer SPA
assets/admin.css    admin styles, reusing the customer design tokens
src/admin/          admin app: api transport, ui helpers, router, pages
src/data/analytics.js  NEW  the client collector
```

**The dependency rule:** routes call services, services call `_lib` and
`_schema`, `_schema` calls nothing. A route never touches Firestore directly.

## 5. Collections

| Collection | Ownership | Rules |
| --- | --- | --- |
| `users/{uid}` | owner writes, server corrects | owner read/write, server fields blocked |
| `subscriptions/{orderId}` | server | owner read, no client write |
| `payments/{paymentId}` | server | owner read, no client write |
| `adminUsers/{uid}` | server | **closed both ways** |
| `adminAuditLog/{id}` | server, append-only | **closed both ways** |
| `analyticsEvents/{id}` | server | **closed both ways** |
| `analyticsDaily/{YYYY-MM-DD}` | server | **closed both ways** |
| `visitorSessions/{sessionId}` | server | **closed both ways** |
| `missingModelRequests/{key}` | server | **closed both ways** |
| `aiTasks/{id}` | server | **closed both ways** |
| `rateLimits/{bucket}` | server | **closed both ways** |

"Closed both ways" means `allow read, write: if false`. **Including for
administrators** — an admin's browser holds an ordinary Firebase ID token, so
it cannot read one document of admin data. Their authority lives on the server.
The consequence: there is no rule here that can be got wrong in a way that
leaks, because there is no condition to get wrong.

### Indexes

`firestore.indexes.json` carries 33 new composite indexes: user filter/sort
pairs, one single-field index per search mirror, payment and subscription
lookups, analytics by type and by user, and the review queues.

**Aggregation queries need the same indexes ordinary queries do.** Until they
are built, `count()` and `sum()` throw `FAILED_PRECONDITION` — which
`metrics-service.js` catches and reports as `null`, so the dashboard shows an
em dash and a banner rather than a 500.

```bash
firebase deploy --only firestore:indexes,firestore:rules
```

## 6. Authorization

```
browser                    server
───────                    ──────
Firebase ID token   ──▶    1. verifyIdToken(token, checkRevoked: true)
                           2. decoded.email is OWNER_EMAIL and verified?
                                yes ──▶ super_admin. Done. No document needed.
                           3. OWNER_ONLY?  ──▶ refuse. (current state)
                           4. custom claim `role` is staff?      ── cheap gate
                           5. adminUsers/{uid} exists, not disabled?  ── authority
                           6. can(role, permission)?
```

### The owner

One account owns this backend: `Stark.ai.India@gmail.com`, named once as
`OWNER_EMAIL` in `api/_schema/roles.js`.

It is matched against `decoded.email` — a claim on a token Firebase has just
verified against Google's signing keys. That is what *Google* asserts the
address is; there is no request field, header or storage key a caller can set
to influence it. `email_verified` is required too: Google sign-in always sets
it, so it costs the owner nothing, and it stops a future password or custom
provider asserting the address without proving control of the mailbox.

The owner needs **no registry document**, so they cannot be locked out by a
missing record or a failed write. And `OWNER_EMAIL` is an address, not a
credential — knowing it grants nothing, because access requires a Google
sign-in *as* that account on every request.

`OWNER_ONLY` is `true`, so the owner is currently the only identity with
access: the registry is not consulted, and a stale custom claim grants nothing.
Setting it to `false` re-enables staff roles, which only the owner can grant.

Every refusal inside the identity gate uses identical wording. A different
message per reason would be an oracle for enumerating who the administrators
are.

### The registry path (dormant)

Two checks, on purpose:

- The **claim** costs nothing and rejects most unauthorised calls without a
  Firestore read.
- The **registry** is the authority. A claim is baked into a token that lives
  up to an hour, so removing someone's access would not take effect until it
  expired. The registry read makes revocation immediate.

A registry document with `disabled: true`, or no document at all, is not an
admin — whatever the token claims.

`setRole` orders its two writes so a crash fails **safe**: granting writes the
registry first, revoking writes the claim first. Either way the failure mode is
"an admin cannot log in", which gets reported in a minute — not "someone can
log in who should not", which nobody reports at all.

### Roles

| Role | Sees | Cannot |
| --- | --- | --- |
| `super_admin` | everything | — |
| `admin` | all business data, all approvals | change roles |
| `support` | users incl. contact details, subscriptions | revenue totals, edits |
| `analyst` | aggregate analytics + revenue | any individual user record |
| `user` | nothing | open the admin area |

`support` and `analyst` are deliberate mirror images: one can help a named
customer without seeing the business's revenue, the other can analyse the
business without seeing the customer list.

Routes ask `can(role, 'users.read')`, never `role === 'admin'`. Adding a sixth
role is one row in `ROLE_PERMISSIONS`, not twenty edits with one missed.

### Reaching the panel

The Account page shows an **Admin Panel** button beside **Edit**, drawn by
`adminLinkHTML()` in `src/app.js` when `SM.fb.isOwner()` is true.

That check decides whether to *draw a link* and nothing else. `/admin` and every
`/api/admin/*` route behind it re-check the same address against the verified
token, server-side, on every request — so conjuring the button in the console
produces a link to a page that refuses you.

The owner address is duplicated between `src/data/firebase.js` and
`api/_schema/roles.js`. Deliberate: the alternative is publishing the owner's
email to every visitor through `/api/firebase-config`, and a link that appears
one render late while a round trip resolves. A test asserts the two never
drift.

`/admin` is not in the SPA's `ROUTES`, so the click interceptor leaves it to
the browser and it loads the separate admin shell.

### Bootstrapping

There is nothing to bootstrap: the owner is recognised from their Google
sign-in. `scripts/grant-admin.js` remains for staff roles once `OWNER_ONLY` is
turned off — it runs with the service-account key, which can already write every
document in the project, so asking it for a password would be theatre.

## 7. Query cost

Deliberate choices, because an admin dashboard that costs more than the product
is one that gets switched off.

| Problem | Approach |
| --- | --- |
| Listing users | Firestore query with cursor paging, **capped at 100** |
| Joining to Firebase Auth | `getUsers()` — one call for the whole page, not one per row |
| Joining to payments | `where('uid', 'in', [...])`, 30 per query — one query for a 25-row page |
| Counting | `count()` aggregation — no documents read |
| Revenue | `sum()` aggregation |
| Growth series | `.select()` projection over the window, capped, `truncated: true` when it bites |
| Top-ten lists | `analyticsDaily` rollups, maintained as events arrive |

**No offset paging.** Firestore's `.offset(500)` reads and bills the 500
documents it skips, so page 20 costs twenty times page 1 and gets worse as the
business grows.

**No full-collection download, anywhere.** Filters Firestore cannot index are
applied server-side after a bounded fetch, and the response carries
`approximate: true` so the UI does not present a page count as a total.

## 8. Analytics

```
browser (src/data/analytics.js)
  · allowlisted event types only
  · search debounced 900 ms  — one event per search, not one per keystroke
  · batched, flushed every 2.5 s, queue capped at 40
  · pagehide → sendBeacon
  · every method swallows its own errors: deleting this file changes nothing
        │
        ▼  POST /api/events   (Authorization optional; a bad token = anonymous)
server
  · rate limit: 60 per session per minute
  · event type must be on the allowlist        ── unknown types rejected
  · metadata filtered field-by-field per type  ── undeclared fields dropped
  · free text redacted for emails and phone numbers
  · timestamp is the SERVER's                  ── clients cannot backdate
  · event id generated here                    ── clients cannot overwrite
        │
        ├──▶ analyticsEvents/{id}     the raw log — the source
        └──▶ analyticsDaily/{day}     counters — a cache, recomputable
```

**Not collected:** IP address, user agent, canvas or font fingerprint, scroll
depth, mouse movement, keystrokes, page content, form values. The session id is
`crypto.randomUUID()` in `sessionStorage` — a random string the browser makes
up for itself, not derived from anything about the device, and per-tab-session
rather than permanent.

An anonymous visitor does not become a registered user. When they later sign
in, `userId` is stamped on the session **going forward**; the pre-sign-in
history is not merged into their profile and the admin UI never presents it as
part of their record.

Two writes per batch: the events, then the rollup. If the rollup fails the
number can be recomputed; if the event fails the request fails. The raw log is
the source, the rollup is a cache.

## 9. What connects next, and how

Each of these is a service in `api/_services/` plus routes in `api/admin/`. None
needs a change to identity, authorization, analytics or the data model.

| Module | Connects through |
| --- | --- |
| Registered-user management | `user-directory-service` — already built |
| Subscription / payment analytics | `metrics-service` + `billing-records` — already built |
| Visitor analytics | `analytics-service` — foundation built, more event types are one row each |
| SEO automation | a new `seo-service`, reading the catalogue + `missingModelRequests` + search demand; drafts become `aiTasks` |
| Instagram inbox / marketing | a new `social-service` behind the official Graph API; drafts become `aiTasks`; no credential in Firestore |
| Ad campaign analysis | a new `campaign-service`; metrics join to `analyticsDaily` by day |
| Business insights | `ai-service` with the `business_insight` capability over aggregates |
| Background jobs | a scheduled function calling the same services — no second data path |

The constraint that makes this work: **every module reads business data through
these services and writes proposals through `aiTasks`.** None of them gets its
own user store, its own auth, or a direct write to the catalogue.

## 10. Deploying this

```bash
# 1. Rules and indexes — do this first; the dashboard degrades without them
firebase deploy --only firestore:rules,firestore:indexes

# 2. Nothing — Stark.ai.India@gmail.com is recognised from its Google sign-in.
#    (grant-admin.js is only for staff roles, once OWNER_ONLY is false.)

# 3. Backfill search mirrors on existing profiles (safe to re-run; dry run first)
node scripts/backfill-user-search.js
node scripts/backfill-user-search.js --write

# 4. Deploy
git push       # Vercel builds from vercel.json
```

Then open `/admin` and sign in with the same Google account.

**Optional, for the AI layer:** set `AI_GATEWAY_URL` and `AI_GATEWAY_TOKEN` —
see `docs/AI-ARCHITECTURE.md`. Everything works without them.

## 11. What was NOT changed

The customer-facing site is intact. Verified: Finder renders, search works,
navigation is unchanged (Finder / Models / Plans / Account), sign-in path
untouched, Razorpay flow untouched, all 45 pre-existing tests pass.

Three additive touches to customer code, and nothing else:

1. `src/data/analytics.js` — a new file, listed in `index.html`, `build.js` and
   `scripts/build-seo.js`.
2. `src/app.js` — `SM.analytics.start()` after boot, and four `track()` calls,
   each guarded by `if (SM.analytics)`.
3. `api/_lib/store.js` — `syncProfile` also writes the derived search mirrors.

The admin app shares exactly three files with the site: the debug logger, the
Firebase auth module and the icon set. It does not load `app.js`, the dataset,
or the catalogue.
